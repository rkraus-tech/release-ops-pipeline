# Project Notes – release-ops-pipeline

## Phase 1 – Planning & repository setup
- Decisions: Jenkins runs natively (apt, systemd) on a dedicated Debian 13 VM `ops01` on the existing Proxmox host `pve01` – realistic always-on build server, Bash runs in the same OS as the deploy target. Docker on the ThinkPad was rejected (Windows/WSL quirks, not always on).
- Database: PostgreSQL instead of SQLite – real DB server with a least-privilege role and proper secret handling.
- Created empty GitHub repo first (no README/license via GitHub) to avoid unrelated histories on the first push; added a placeholder README locally.
- Folder structure: jenkins, scripts, sql, python, app, screenshots, docs (`.gitkeep` files because Git does not track empty folders).
- `.gitattributes` forces LF for all Linux-side files (*.sh, Jenkinsfile, *.py, *.sql). Reason: CRLF from Windows breaks Bash (`$'\r': command not found`). Verified with `git check-attr eol -- scripts/deploy.sh`.
- `.gitignore` excludes secrets (.env, .pgpass, keys), Python caches, runtime logs (except log-scanner samples) and unredacted screenshots (`screenshots/raw/`).
- Both files start with a comment line so a UTF-8 BOM (Windows PowerShell 5.1) cannot invalidate the first rule.

## Phase 2 – Pipeline VM on Proxmox
- Created VM 125 `ops01` on `pve01`: Debian 13 netinst, q35, 2 vCPU (type `host`), 4 GiB RAM, 32 GiB disk on `local-lvm` (VirtIO SCSI single, discard + SSD emulation), VirtIO NIC on `vmbr0`, QEMU guest agent enabled.
- VM ID 125 matches the planned IP 192.168.2.25 – naming convention for quick mapping between VM and address.
- CPU type `host` instead of the default `x86-64-v2-AES`: single-node setup, so live-migration compatibility is not needed; better performance for Java (Jenkins) and SSH.
- Discard + SSD emulation so deleted blocks are returned to the LVM-thin pool via TRIM.
- Installer choices: English system language (searchable error messages and logs), timezone Europe/Berlin (correct timestamps for the deploy history), German keyboard, hostname `ops01.home.arpa` (RFC 8375 home-network domain).
- No root password: root account locked, `sudo` installed automatically for user `robert` – every admin command is logged with the user name.
- Single partition without LVM: flexibility already comes from Proxmox (resize disk in Proxmox, grow the partition in Debian).
- Minimal headless install: only SSH server + standard system utilities, no desktop (smaller attack surface, less RAM, fewer updates).
- Static IP: `/etc/network/interfaces` changed from `allow-hotplug` + `inet dhcp` to `auto` + `inet static` (192.168.2.25/24, gateway 192.168.2.1). `auto` makes boot wait for the network. Backup created first (`interfaces.bak`).
- Enabled "Start at boot", ejected the installation ISO, verified the IP via the guest agent in the Proxmox summary, switched to SSH for all further work.

### Challenge: DNS lost after reboot
- Symptom: after reboot, `ping deb.debian.org` failed with "Temporary failure in name resolution", while `ping 192.168.2.1` worked.
- Diagnosis: `/etc/resolv.conf` header showed "Generated by dhcpcd". dhcpcd is still started at boot for IPv6 (`iface ens18 inet6 auto`) and rewrote the file – without any IPv4 nameserver.
- First fix attempt (`nohook resolv.conf` in `/etc/dhcpcd.conf`) did not work: `tail /etc/dhcpcd.conf` revealed a typo (`nohohook`), which dhcpcd silently ignores.
- Solution: corrected the line to `nohook resolv.conf`, wrote `/etc/resolv.conf` manually (`search home.arpa`, `nameserver 192.168.2.1`), verified after reboot.
- Lesson: always verify config changes after a reboot, and check the actual file content instead of assuming a command worked.

## Phase 3 – Jenkins & sample app
- Installed `openjdk-21-jre-headless` + `fontconfig` before Jenkins: current Jenkins LTS requires Java 21+; headless JRE because the server only runs Java and has no GUI; fontconfig is needed by Jenkins for rendering graphs.
- Added the official Jenkins LTS apt repository (`debian-stable`) with a dedicated keyring (`signed-by=/etc/apt/keyrings/jenkins-keyring.asc`) so the key is trusted only for this source. LTS instead of weekly for stability.
- `Ign: ... InRelease` during `apt update` is expected: the Jenkins repo provides `Release` + `Release.gpg` instead of `InRelease`; signature verified (no NO_PUBKEY).
- Jenkins runs as systemd service under the unprivileged `jenkins` user (least privilege), listening on port 8080. Note: Jenkins logs in UTC, systemd in local time.
- Unlocked with the one-time `initialAdminPassword`, installed suggested plugins (Pipeline, Git, Credentials, Timestamper, ...), created a personal admin account instead of the default `admin`.
- Installed nginx as deploy target, plus `curl` (HTTP checks) and `jq` (JSON parsing for the health check) – both missing in the minimal install.
- Release layout: `/opt/release-app/releases/<version>/` + symlink `/opt/release-app/current`. Switching the symlink is atomic; rollback = pointing the symlink back. Directory owned by `jenkins`, so deployments need no sudo.
- nginx site `release-app`: root `/opt/release-app/current`, `/health` serves `health.json` with `Cache-Control: no-store`, dedicated access/error logs (input for the Python log scanner). Disabled the default site, validated with `nginx -t`, applied with `reload` (no dropped connections).
- Expected `404` before the first release confirmed the new config was active.
- Sample app in `/app`: `VERSION` (single source of truth), `index.html` and `health.json` with placeholders (`__VERSION__`, `__BUILD__`, `__BUILT_AT__`) that the build stamps.
- Files written via `[IO.File]::WriteAllText` because Windows PowerShell 5.1 `Set-Content -Encoding utf8` adds a BOM, which breaks JSON parsing with `jq`.

## Phase 4 – Build, deploy & rollback scripts (Bash)
- Split into `build.sh` (package once) and `deploy.sh` (deploy that exact artifact) – "build once, deploy many".
- `build.sh`: reads `app/VERSION`, build number from argument or Jenkins `BUILD_NUMBER`, release id `<version>-b<build>` (unique per build). Stamps placeholders with `sed` in a temp staging dir (cleaned up via `trap ... EXIT`). Quality gates: fails on leftover placeholders or invalid JSON (`jq empty`). Produces `tar.gz` + `.sha256`. Logs to stderr, artifact path to stdout (machine-readable for Jenkins).
- `deploy.sh deploy|rollback|status`, all scripts use `set -Eeuo pipefail`.
- Deploy flow: `flock` lock (no parallel deploys) -> checksum verification -> unpack into `<id>.tmp` and rename (no half-unpacked releases) -> normalize permissions (`chmod -R u=rwX,go=rX`, never trust artifact permissions) -> atomic symlink switch (`ln -sfn` + `mv -T`) -> health check -> cleanup (keep 5 newest).
- Health check verifies that `/health` reports `status=ok` AND the expected version and build number – "responds" is not enough, it must be the right release. 5 attempts, 2 s apart.
- Automatic rollback when the health check fails: switch back to the previous release, verify it, mark the bad one as `<id>.failed` (kept for analysis, never offered as rollback target).
- Exit codes for Jenkins: 0 success, 1 error before any change, 2 failed but rolled back, 3 critical (rollback failed too).
- Logs with timestamp + level to stderr and `/var/log/release-app/deploy.log` (owned by `jenkins`).
- Optional `record-deploy.sh` hook for the database (Phase 5); recording errors only produce a warning and never fail a deployment.
- Git on Windows does not store the executable bit -> `git update-index --chmod=+x scripts/*.sh`, verified with `git ls-files -s` (mode 100755).
- Tested on `ops01` as the `jenkins` user (`sudo -u jenkins`) to reproduce the exact permissions Jenkins will have. Installed `git` on the VM (needed later by Jenkins).
- Test results: 1.0.0-b1 and 1.1.0-b2 deployed without nginx restart; intentionally broken 1.1.0-b3 (`"status": "degraded"`) was detected and rolled back automatically in 10 s (exit code 2); manual rollback 1.1.0-b2 -> 1.0.0-b1 in < 1 s.

### Challenge: wrong terminal
- Ran `sed` in the local Windows PowerShell instead of the SSH session -> `CommandNotFoundException`. Harmless, but it would have modified the real repo file. Lesson: always check the prompt (`PS C:\...` = local, `robert@ops01` = server) before running commands.

## Phase 5 – Deploy history in PostgreSQL
- Installed PostgreSQL 17 (Debian default). Listens only on 127.0.0.1/::1 (not reachable from the LAN). `postgresql.service` shows `active (exited)` by design – it is an umbrella unit for `postgresql@17-main`.
- Decision: peer authentication over the local Unix socket instead of passwords. The Linux user `jenkins` logs in as DB role `jenkins` – no secret exists that could leak. Debian initializes clusters with `--auth-local peer` already. For a remote/central DB, password auth with the password stored in Jenkins Credentials would be used instead (never in scripts or the repo).
- Role concept (least privilege, group-based): `deploy_writer` (INSERT + SELECT) and `deploy_reader` (SELECT only) as NOLOGIN group roles; login roles `jenkins` (writer) and `robert` (reader). `REVOKE ALL ON DATABASE releases FROM PUBLIC`, CONNECT only for the two groups.
- Table `deploy_history`: id (identity), deployed_at (timestamptz), action, release_id, version, status, duration_s, previous_release, triggered_by (default `current_user`, cannot be faked with peer auth), build_url. CHECK constraints reject invalid action/status values and negative durations. Index on deployed_at.
- Append-only audit log: nobody except the owner may UPDATE or DELETE. Verified with `\dp` (`deploy_writer=ar`, `deploy_reader=r`) and a failed INSERT as `robert` (permission denied).
- Schema scripts run with `psql -X -v ON_ERROR_STOP=1`; table creation wrapped in BEGIN/COMMIT.
- `scripts/record-deploy.sh`: hook called by `deploy.sh`. Values passed as psql variables (`:'var'`) -> safe against SQL injection (tested with `'; DROP TABLE x;--`). `PGCONNECT_TIMEOUT=5`, Jenkins `BUILD_URL` stored when available. DB errors only cause a warning in `deploy.sh`.
- `sql/reports.sql`: last 10 deployments, success rate (30 days), average/max duration per action and status, currently live release.
- Test: rollback to 1.1.0-b2, deploy 1.0.0-b4, intentionally broken 1.0.0-b5 (auto rollback, status `rolled_back`, 10 s) – all three recorded automatically.

### Challenge: commit not pushed
- `git pull` on ops01 did not bring the new SQL files -> `psql: No such file or directory`. `git status` on the ThinkPad showed "ahead of 'origin/main' by 1 commit": the commit existed locally but was never pushed.
- Lesson: after every push, check for "up to date with 'origin/main'". Rule of thumb: push on the workstation, pull on the server.

## Phase 6 – Jenkins pipeline
- Declarative pipeline as code in `jenkins/Jenkinsfile` (versioned, reviewable, restorable). Job `release-app` = "Pipeline script from SCM" (Git, branch `*/main`, script path `jenkins/Jenkinsfile`, no credentials – public repo).
- Stages: Lint (`bash -n` + ShellCheck) -> Build (`build.sh $BUILD_NUMBER`) -> Archive (artifact + sha256, fingerprinted) -> Deploy (`deploy.sh deploy`) | Rollback (`deploy.sh rollback`). `post { always }` prints `deploy.sh status`.
- Options: `disableConcurrentBuilds`, `timestamps`, 15 min timeout, keep last 30 builds.
- Parameters: `ACTION` (deploy/rollback), `ROLLBACK_TO` (empty = previous release). Exit codes of deploy.sh are translated into clear build descriptions and errors (exit 2 = "FAILED - automatically rolled back", exit 3 = "CRITICAL").
- Trigger decision: Poll SCM (`H/2 * * * *`) instead of a GitHub webhook – a webhook would require exposing the build server to the internet; polling only needs outbound connections. In a company network an internal Git server would send webhooks.
- Pitfall: parameters and triggers from a Jenkinsfile are only registered after the first run ("Build Now" first, then "Build with Parameters" appears).
- Go-live preparation: Jenkins build numbers start at 1 and would collide with the manual test releases -> removed test releases, `TRUNCATE deploy_history RESTART IDENTITY` (only possible as DB admin), emptied deploy.log.
- End-to-end test:
  - #1 initial deploy 1.0.0-b1 (manual start)
  - #2 commit "release: 1.1.0" -> started automatically by SCM change -> 1.1.0-b2 live (5.4 s)
  - #3 faulty commit (health status "degraded") -> deploy failed, automatic rollback to 1.1.0-b2, build red, users never saw the broken version
  - #4 fix via `git revert` (new commit, honest history; no history rewrite on shared branches) -> 1.1.0-b4 live
  - #5 manual rollback via "Build with Parameters" -> back to 1.1.0-b2 (failed b3 skipped as rollback target)

### Challenge: commits not pushed
- Polling log showed "already built by 1" – the remote head had not changed because the commit was only local.
- Fix: always run `git push` + `git status` ("up to date with 'origin/main'") after committing. The Jenkins "Git Polling Log" is the place to check what Jenkins actually sees.
